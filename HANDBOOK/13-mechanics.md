## 13.1 Event bus protocol

The event bus is an append-only JSONL file at `runs/{runId}/events.jsonl`.

**Append protocol (`appendChained` in `@qa/event-bus`, called by the aegis CLI and `@qa/reporters.writeArtifact`):**
1. Validate the event against `AegisEventSchema`; refuse undeclared fields and caller-set envelope fields (nothing is written on a refusal)
2. Acquire the `proper-lockfile` lock on the log (stale 5s)
3. Refuse a torn tail (an unterminated, unparseable last line); the owner cuts it with `aegis integrity repair-tail` (whatever the run status), which keeps the bytes in the run's integrity directory and records `integrity.tail-repaired`
4. Append one line with the envelope `seq`, `prevHash` (sha256 of the previous line), `emittedBy` and `runId`
5. Release the lock

Every event includes `ts: string` (ISO-8601 UTC). No agent overwrites another's events. Reads are unrestricted and concurrent; only writes are serialized.

**Reading:**
```typescript
import { readAll, tail, typeFilter } from '@qa/event-bus';
const events = readAll(busPath, typeFilter('task.claimed', 'task.released'));
for await (const evt of tail(busPath)) { /* stream */ }
```

## 13.2 Taskmaster task claim/release atomicity

Task files live at `runs/{runId}/taskmaster/tasks/{id}.json` and change only through the `aegis task` commands:

- `aegis task add --id <id> --title <text> --agent <qa-*>` — the dispatcher adds a task for one assignee, tagged with the phase in progress. The assignee is the only agent that may claim it; its paired SPV reviews it.
- `aegis task claim --task <id>` — the assignee takes a `pending` task (`not-assignee` for anyone else), under the task-file lock; the specialist cap and the environment rules apply. Records `task.claimed`. An agent claiming a task it already holds is told `already-claimed` (a resumed worker continues without claiming); when the hook ledger shows the claim held by another live instance of the same agent, the second instance is refused with `duplicate-dispatch` and stops without doing the work. A specialist claim also counts the live dispatch reservations of other tasks against the cap (`cap-reached`), so a claim without a dispatch cannot take a reserved slot.
- `aegis task release --task <id> --result done|failed` — after a work report from this claim. `done`: the task was carried out (failing tests are results of a `done` task). `failed`: the agent could not complete the task; the CLI opens an escalation for that attempt and blocks the run until the owner decides with `/qa-escalation`. Records `task.released`.
- `aegis task cancel --task <id> --reason <text>` — the task's creator withdraws a `pending` task nobody ever claimed. Records `task.cancelled`; the phase barrier ignores the task. It also withdraws an in-progress task whose holder has ended (see "Ended instances" below) and that holds no work report awaiting review; `aegis task abandon` (owner) stays open for any in-progress task without such a report.
- `aegis task list [--run <id>] [--phase <id>]` — read-only, any caller: the run's tasks as JSON (id, title, phase, assignee, status, claimedBy, createdBy, latest attempt, the review state of that attempt — `none`, `passed`, `requested-changes`, `escalated` or `accepted-with-risk` — and the owner's escalation decision with its reason). Dispatchers use it to recover after an interruption. Takes no lock and writes nothing.
- `aegis task next [--phase <id>] [--wait <seconds>]` — read-only, `qa-test-executor` and the owner: the Execution dispatch loop as JSON. `mode` (`aegis.config.json#execution.dispatchMode`: `batch`, the default when the key is absent, or `continuous`; any other value, and any other key under `execution`, is refused by name where the setting is used: `task next`, the dispatch check, and `run create` for the owner; `aegis env exec`, the seed check and every `task claim` never read it, H1 never reads it, and H2 reads it only for the executor's stop check, where a bad value lets the stop through with a warning that names the setting (the executor loop guard is off until the owner fixes it); a bad value never denies a write or traps an agent), `cap` and `freeSlots` (specialist slots neither claimed nor reserved, over the whole run, as the claim counts them); `specialistTasks` (the phase's specialist tasks); the specialist tasks of the phase under `running` (claimed, holder live), `dispatched` (reserved, not claimed yet), `dispatch` (offered now: at most `freeSlots` pending tasks, `corrective` when the latest attempt was sent back, plus `resume` entries, in-progress tasks whose holder ended, which need no slot), `waiting` (pending beyond the free slots), `review` (released `done`, unreviewed, no SPV running: dispatch its SPV now), `reviewing` (an instance of its SPV started after the release), `redrive` and `failedRelease` (marked `inFlight` while an instance of the SPV, or of the assignee, started after the rejection or the failed release is alive), `held` (batch mode: released tasks whose SPV waits until the whole wave has returned), `escalated`, `settled`, and `recover` (each in-progress task whose holder ended, with its `problem` and the exact `fix`); and `next`: `act`, `wait`, `blocked` (an open escalation, a blocked run or a stop request; `reason` says whether work is still in flight) or `settled` (every specialist task passed, accepted with risk or cancelled; with `specialistTasks` 0, `reason` says so: `task next` knows only tasks already added, so the executor adds every specialist task before its first call). The mode decides what is offered: in `continuous` mode every free slot is offered at once and a released task's SPV at once; in `batch` mode a wave fills up to the free slots until one of its tasks comes back; from then nothing new is offered (no refill): a released task waits in `held` while a member still runs, is reserved or is to be resumed, the wave's SPVs are offered once it has returned, and the next wave only when no task awaits its SPV (held, review, reviewing or any redrive). While the loop is blocked nothing is offered. The dispatch reservation accepts a specialist dispatch exactly when `task next` offers it (a state-generated test checks offer and verdict over every combination in both modes): `cap-reached` when no slot is free, `batch-wave-open` in batch mode, `not-offered` in continuous mode for a task the offer lists behind others. The guards below (reservation, cap with reservations, duplicate claim, ended instances, H2) apply in both modes. `--wait` (at most 540) returns at once only when something is actionable now (`act`, `settled`, or `blocked` with nothing in flight); otherwise it returns as soon as the view changes or after the given seconds. It polls the files in its own process, holds no lock and spawns nothing. Takes no lock and writes nothing.
- **Dispatch reservation.** `aegis event append --type specialist.dispatched` is checked under the claims lock before it is recorded: the task (`taskId`, required) must be a specialist task assigned to `specialistName`, and either pending with no live reservation and a free slot, or in progress with a claim holder that ended (a resume, no slot). Otherwise it is refused: `already-dispatched`, `already-running`, `cap-reached`, or the task's state. A recorded dispatch carries `reserved: true`, stamped by the CLI (the marker of this protocol in a run's log). Each open reservation is tied to the first instance of its specialist that starts within 5 minutes after it (oldest reservation first, one instance each): it lives while that instance lives and until the task is claimed; with no instance started within the 5 minutes it is released. So the executor appends the event first and makes the `Agent` call only when it is recorded; the claim cap stays the hard limit. `aegis task add` records `createdAt` in the task file (absent on tasks of earlier runs).
- **Ended instances.** The hook ledger gets an end entry only from SubagentStop, which a dying session (crash, authentication failure, killed terminal) never fires. Every hook entry (`start` from H4, `claim` and `heartbeat` from H1) records the Claude Code `session` of its call (the payload's `session_id`, else the name of the session transcript file), and H1 records the session that runs `aegis run resume` (a `run-resume` entry of the main thread). **At a resume:** a `run.resumed` means the owner restarted orchestration (`/qa-resume` hands the run to a new orchestrator), so at every resume (a) every orchestrator and `qa-test-executor` instance first seen before it is ended, unconditionally: they are superseded by the new orchestrator and the executor it dispatches; (b) any other instance is ended when its session differs from the resuming one, or, in the same session or without session data, when its latest entry at or before the resume is older than 90 seconds (`RESUME_FRESH_MS`). Every real crash-and-resume so far was in the same session (`claude --continue` keeps the session id; agents died of `authentication_failed` or "[Request interrupted by user]" while the session lived), and this rule ends those dead agents at once. Limit: a specialist alive inside one long call at the moment of the resume (its latest entry more than 90 seconds old) is ended too, as part of the owner's explicit restart, and its task is offered for resume; its completed work is still accepted, because work-report submit and task release check the claiming agent type, never the instance. In a run with no heartbeat data every instance first seen before the resume is ended. A resume end is permanent: a later entry never revives it. **Heartbeats and expiry:** H1 (PreToolUse) appends a `heartbeat` for a qa-* instance at most every 30 seconds, on the calls its matcher covers (Write, Edit, MultiEdit, NotebookEdit, Bash, Agent, Task; Read, Grep, Glob, Skill and MCP calls fire no hook). The throttle reads the ledger's last 64 KB for the instance's latest heartbeat (one stamped in the future counts as expired, a torn line is skipped, one further back costs one extra line); no marker file is kept, and the append never fails or delays the call. In a heartbeat run an instance silent for 30 minutes (`LIVENESS_GRACE_MS`; real agents that later completed were silent up to 49.7 minutes, 2 of 1,824 over 30) is ended at its latest entry plus 30 minutes, and its task is offered for resume. A later entry (a beat after the stall) revives it only if nobody took its task over meanwhile: no `specialist.dispatched` accepted and no claim by another instance for a task it claimed, between the expiry and that entry; once taken over, the end is permanent. The orchestrator and `qa-test-executor`, which can wait hours in one foreground `Agent` call, never expire (`NO_EXPIRY_AGENTS`): they end only by their stop record or at the next resume. A stop request alone ends nothing, and nothing is written to the ledger for an end. The constants are in `packages/@qa/run-state/src/claim-holder.ts`. `aegis task next`, the dispatch reservation, `task claim` and H2 apply the same rule. An in-progress task whose holder ended, or with no ledger holder and a claim older than the latest resume, is offered as `resume` (never `running`), a new instance claiming it is told `already-claimed` (continue), and its creator may cancel it.

If an agent crashes after claiming but before releasing, the orphan lock is detected by `/qa-health --fix` (stale lock age > 5 minutes).

## 13.3 Path-guard enforcement

Writes are enforced by the PreToolUse hook `scripts/hooks/guard-writes.mjs` (H1). It applies the role table in
`packages/@qa/path-guard/src/roles.ts` to every `Write`, `Edit`, `MultiEdit`, `NotebookEdit` and `Bash` call and checks
every `Agent` dispatch. Exit 2 denies the call with the reason.

- A call that carries a non-empty `agent_id` (of any type) is a subagent's, and its `agent_type` names the caller; a
  call without one is the main thread (a `--agent` session included).
- Run files the CLI owns — `events.jsonl`, `run.json`, `gates/`, `reports/work/`, `reports/review/`, `reports/lint/`, `reports/explore/`, `reports/env/`, `taskmaster/`,
  `intake/`, `hooks/`, `integrity/`, the case and scenario Markdown (`cases/TC-*.md`, `scenarios/SCN-*.md`, rendered from their JSON by
  `aegis cases render`), lock files and the active-run pointer — are refused for every caller. A `find` with `-delete` or a changing
  `-exec` from `cases/` or `scenarios/` is refused for a subagent (the main thread's `find` is not checked), since it reaches that
  Markdown; removing or moving `cases/` or `scenarios/` itself is refused for every caller.
- Customer-facing files (`plan.*`, `rtm.*`, `cases/`, `defects/`, `reports/closure/`, `reports/executive/`, `reports/compliance/`) are refused
  when the written text matches a brand-exposure pattern.
- Tooling wording is refused too in `defects/`, `reports/closure/` and `reports/compliance/` (`TOOLING_WORD_PATTERNS` in `@qa/contracts`, checked by H1): CLI, defectMap, event sequence numbers (`seq 784`), `framework defect`, `cli.refused` or refusal counts, review and attempt counts, SPV, `requested changes`, work report and "record owner". Tooling facts belong in events and work reports. It also refuses a path or file name of a run or framework file (`reports/metrics|work|review|closure|compliance|mutation|executive/...`, also after `runs/<run-id>/`; a glob over run files such as `cases/*.json`; `coverage.json`, `rtm.json`, `rtm.md`, `closure.json`, `events.jsonl`, `run.json`, `triage-summary.md`, a `*-result.json` that names no case) and a local-server reference (`localhost`, `127.0.0.1`, `[::1]`, `0.0.0.0`, `port 3002`, and a colon-prefixed port the project lists in reportRules.localPorts, such as `:3002`; a bare number is never flagged), and says what to write instead (the coverage summary, the traceability matrix, the defect records, the triage summary, the case result files, the local test server). In JSON a whitespace-free value under a data key (`evidence`, `logs`, `report`, `unavailableMetrics`, ...) is data and exempt. The local ports are project config: reportRules.localPorts in aegis.config.json (default none) lists the ports flagged colon-prefixed; an unlisted `:N` and a bare number are never flagged, a CIDR range (`0.0.0.0/0`) is not a host, and a low port such as `:22` would also match a clock time, so list ports of 1024 or above; H1, the three report scripts and the executive checker read the same list, and the scripts exit 2 on an unreadable config or a malformed list. The path and port rules apply to customer-facing documents, not to defect reproduction data: in a defect record (`defects/DEF-*`) every field but the title takes only the tooling words (not "attempt count" either, which an application can have), because its steps, ruled-out notes, build line and history cite the URL, local server or file a developer needs; the append-only audit fields of a record, `history` and `investigationLog` (and the Markdown sections of those names), are not read for tooling words at all (no report prints them, `aegis defect amend` never changes them and an old entry cannot be reworded; the brand rule and the personal-data rules still read them); the title takes every rule (the technical report and the sign-off print it), also in an Edit fragment that carries a `"title"` member or is a lone string value (which the hook cannot place and so checks fully) and in a fragment that carries the markdown record's first `# ` heading. A fragment that is only part of the title text (no member, no quotes, no heading) reaches H1 without its field, so H1 checks it with the word rules only; the pre-gate lint is the backstop: it reads the whole record and the title takes every rule there as an error (at G2, and at the Closure-final barrier for a title edited after Triage). `aegis defect amend` checks its new values the same way (the title is not amendable). The triage summary keeps every rule. The same list is the guard of the technical-report, sign-off and deck scripts: they run it over `closure.json` (or `executive-deck.json`) before rendering and exit 7, 9 and 10 with the first 5 offending phrases and their fields. The path rules are deliberately narrow: citing proof is how a defect record or a compliance report works, so `evidence/...` and `runs/<run-id>/evidence/...` paths and `cases/<TC-id>...` and `defects/<DEF-id>...` references (a case result `TC-AUTH-001-result.json` included) are never flagged; only the bookkeeping names (`coverage.json`, `rtm.*`, `closure.*`, `run.json`, `events.jsonl`, `execution-summary.*`, `triage-summary.md`, `risk-register.*`, the metric files), `reports/metrics|work|review|closure|compliance|mutation|executive` paths, globs and ports are. **Tier 2:** the sign-off script (exit 9) and the deck script (exit 10) also refuse engineering vocabulary (oracle, stub, mutant, CAPITAL_SNAKE_CASE setting names, HTTP status numbers (also beside the verb that met them, "denied with 403", or their Title-Case name, "429 Too Many Requests"; only a known status, 200, 201, 204, 301, 302, 304, 400, 401, 403, 404, 405, 409, 410, 422, 423, 429, 500, 502, 503 or 504, with a status cue, so "blocked by 250 duplicate records" and "400 conflict cases" are counts), "endpoint" (not a study or trial endpoint), "rate limiting", "fail closed", CWE-/WSTG- ids, `/api/` paths, snake_case codes, "exit code", "build cache", "bypass module", "HTTP route", "no PR", "NRIC/SPD", a bare `SevN`, the noun "blocker" for what stopped a check (the severity name is allowed: "(Blocker)", "1 Blocker", "Blocker and Critical defects", "the Blocker defect", "severity Blocker"), "no ship / no-ship") in the closure fields the sign-off prints (`exitCriteria[].criterion` and an unmet criterion's `evidence`, `variancesFromPlan`, `resultsSummary.caseOfRecord.basis` and `.outOfScope[].reason`, the case-figures `reconciliations` entry, `residualRiskSummary[].title` and the executive reporter's plain risk sentences) or in the deck content, each with its plain replacement. The technical report is an engineering document and uses tier 1 only. A closure sentence that points to one of its own numbered sections ("section 6") is rewritten to "the closure report" in both documents, which have no numbered sections; a legal ("section 24 of the PDPA") or lettered ("section 26C") reference is kept. The sign-off lists each open application defect (id, severity word, state, title, what it awaits) and prints a `falsePasses` entry that carries a wrong test step (the lockout check) in both documents. The technical report is tier 1 only; its accepted vocabulary (HTTP status numbers, route paths, CWE ids, code strings, oracle, stub) is listed in the executive reporter and its SPV. Both documents state "This document gives no release recommendation and no compliance verdict." and no longer quote the closure's compliance note. A bare severity code ("Sev1") and the word "blocker" are not in tier 1 (a defect record carries codes as data); the shared wording rule forbids them in prose and the SPVs check it. Oracle, stub, mutation score and HTTP status numbers stay allowed. The list is deliberately narrow (it does not flag the plain word "framework" or "sequence"); it can still hit a target that has its own "CLI" or a "work report" feature, and then the author words it differently ("command-line tool"). **The pre-gate lint** (`aegis lint run --gate G2|G3`, the Triage and Closure-final barriers and the gate opening) reports the same rules over the files as written: `brand-name` over every brand-clean file (an error; a warning in a case result file, a working record); `tooling-tier1` over the defects, closure and compliance files and the two executive inputs (`executive-deck.json`, `residual-risks.json`), never over cases, the plan or the RTM, which cite the local server and run files on purpose. A JSON file is read by its parsed string values, so the data-key exemption holds. The wording rules (QA-process words, internal task ids, the manual-testing rule) read prose a person wrote, so they skip what nobody can reword: a defect record's `history` and `investigationLog` (and the Markdown sections of those names), the value of a `charterSessionId` field, a whitespace-free value under a data key of a JSON file (`evidence`, `file` ...) and, for the internal task id rule, an id inside a file name or path that ends in a file extension (an evidence file, exploratory notes), all names the framework generates; a task id in a sentence is still an error, in the closure, the compliance reports, the plan and every other field of a defect. The personal-data rules and the brand rule read every field. The personal-data rules also read the fake phone and email of the messaging block of aegis.config.json (messaging fakeRecipients) as declared synthetic values, like reportRules.pii.syntheticValues, and never print them. Severity: an error in the closure and the triage summary; in a defect record the title (and the markdown record's first `# ` heading) takes every rule as an error, a tooling word elsewhere is an error, a path or server elsewhere a warning, and the process rule is left out; every compliance hit and every hit in the executive inputs (written only by the executive reporter, after G3) is a warning. H1 itself refuses every tier-1 kind on a write to `reports/compliance/**` (paths and ports included; the defect-record exception does not apply there), so a compliance warning covers only a file that reached the run another way. At G3 the closure fields the sign-off prints (the list above, plus the open-defect lines: `defectMetrics.openItems[].title` and `.awaits`, or, when the closure lists no open item, the titles of the open defects in the defect log) take `tooling-tier1` and `tooling-tier2` as errors without blanking quoted or backticked text, because the executive phase comes after G3 and the closure is the source the closure reporter can still fix: a defect-log title is reported on the closure, and listing `defectMetrics.openItems` with a plain title replaces it in the sign-off. The executive reporter's plain risk sentences (`residual-risks.json`), which replace the closure's risk titles once they exist, are read the same way as warnings: only the executive reporter writes them, and the executive stage holds them. **The executive stage** (`aegis lint run --stage executive`, run by the orchestrator or the owner after G3, once the executive phase has started and never in a smoke run; the report is `reports/lint/stage-executive.json` and `lint.completed` carries `stage` instead of `gate`) reads `executive-deck.json` and `residual-risks.json` as written, quoted text included, with `tooling-tier1`, `tooling-tier2` and `brand-name` as errors and the general wording rules (the QA-process words, internal task ids ...) as warnings, because no render script enforces those; the closure fields and open-defect lines the sign-off prints are warnings there, because only an owner reissue changes the closure after G3. It also checks `exec-residual-risk-ids` (the ids of `residual-risks.json` are exactly the closure's `residualRiskSummary` ids, none missing, extra or repeated), `exec-risk-one-sentence` (one sentence per entry of `residual-risks.json`; the deck's residual risks are never checked, they carry no ids and may run longer) and `exec-report-event-missing` (for each of the technical report, the sign-off and the deck, a `report.produced` or `report.fallback` event since the latest start of the executive phase; one attempt may re-render a single deliverable). It reads no PDF: the rendered documents are checked by the conditions checker the reporter and its reviewer run. The executive phase does not complete while the executive stage has an error (its warnings never block); the stage is computed once, before the run lock. **At submit** the closure reporter, the executive reporter, the six compliance agents and the defect manager see the same lint over the files their work report's `artifactsProduced` names (run-relative or with the run prefix, a directory or a glob; Markdown and JSON only; with none named, the files of their role), with the run-level classification of each file and no case rendered; the closure reporter also gets the G3 scan of the closure fields the sign-off prints, and the executive reporter the executive stage. A path through a symbolic link, or out of the run, is never read. A smoke run is not linted at submit. The submit result lists the findings under `lint`, the CLI stamps the error ids into the stored work report as `lintErrors` (one an agent writes is dropped; it lists only findings the writer can fix: the audit fields of a defect record and the generated identifiers are never in it), and the submit is never refused, because a refused submit would leave the task unreleasable. A fix and a new submit within the same claim is the next attempt, which the review attaches to; a reviewer returns a stamped report as requested-changes without a deep review. Tier 2 never reads the technical report or the compliance files. reportRules.disable switches each rule id off and reportRules.allow silences a phrase, in the lint only: H1 and the three report scripts read neither, so for `brand-name`, `tooling-tier1` and `tooling-tier2` a disable or allow would only move the refusal to the write or to the render after G3. A gate or the executive barrier therefore never offers an exception for these three; the way out is fixing the wording (after a gate, the owner reopens the phase that wrote the file). For the other rule ids a refusal names the exception. Every open question in those files asks a decision of a named audience (PM, owner or developers) and says what changes with each answer.
- A work report carries only the keys of its schema: any other top-level key (a `findings` list, for one) is not stored, and `aegis work-report submit` names each dropped key in `droppedKeys` of its result so the worker moves the content into a key that is kept.
- `aegis event append --type <type>` takes the event fields from `--json '<object>'` or from `--json-file <path>` (a UTF-8 file of at most 1 MB; `--json-file /dev/stdin` reads a heredoc), never both and never neither (an event with no fields is `--json {}`); both go through the same validation. A refused event names each field and its limit, for example `component: longer than 200 characters (got 250)`; a free-text field over its limit is cut and listed in `trimmed`, while a path, a command or a grouping key (`evidence`, `component`, `path`) is refused instead of cut. The cheat-sheet each agent starts with lists the finding severity, uncertainty impact and review verdict enums, the timestamp format and the lesson id pattern, read from the schemas.
- A refusal an agent receives is recorded on the run as `cli.refused`, with every value the caller gave cut out of its message (`<value>`), so a refusal that quotes a field never keeps the value in the append-only log. What counts as given: the command line, and the text of every file or standard input a command reads for the caller, read raw before any check, also when it does not parse: `--json-file` of `aegis event append`, and `--file` of `aegis work-report submit` and `aegis review submit` (a path or `/dev/stdin`; at most 16 MB). The field names the event, work report and review schemas declare stay readable in the message; any other key the caller wrote is cut out too.
- The main thread never writes a run directory or the target's `tests/`; a subagent whose name does not start with
  `qa-` never writes inside this repo either. Rollout exception: the direct run writes of the skills not yet rewritten
  onto the CLI (`LEGACY_MAIN_THREAD_RUN_WRITES` in `packages/@qa/path-guard/src/guard.ts`) are allowed from the main
  thread with a warning and a `legacy-write` hook-ledger entry; P0c/P3 remove each skill's entry when they rewrite it.
  The two files git tracks in the runs directory, its `README.md` and `.gitkeep`, are framework files: the main thread
  may edit them, restore them with `git checkout`/`git restore` and `git rm` them.
- The main thread never writes target source either: anything inside the target outside this repo, the tests
  directories, the QA-owned `qa-*.yml` workflow files and the `/qa-push-reports` collector repo named by
  `aegis.config.json#collector.path` (with no such key there is no collector exception). The target's Playwright
  config is the environment engineer's alone.
- A `qa-*` agent writes only its role row's globs — {run} is the active run, {testsDir} is
  `aegis.config.json#testsDir`, {target} is `targetProjectRoot` — or the OS temp directory; never `packages/`, `apps/`,
  `.claude/`, a `package.json` or a lockfile, and nothing at all while the run's environment forbids it.
- No role row covers the copied QA helpers `{testsDir}/support/test-helpers.ts` and `{testsDir}/support/supabase.ts`.
  Only `aegis helpers vendor` writes them, and only `qa-environment-engineer` may run it (in Env-auth); it overwrites a
  hand-edited copy and reports it as drift.
- A `qa-*` agent never changes dependencies in this repo or the target: `pnpm`, `npm`, `yarn` or `bun` with `add`,
  `install`, `ci`, `remove`, `update`, `link`, `unlink` (or an alias) is refused when its directory (the command's
  cwd, or `-C`/`--dir`/`--prefix`/`--cwd`) is inside either and outside the sandbox. A global install (`-g`,
  `--global`) is allowed: the environment engineer's `npm install -g @playwright/cli` is one.
- A `task claim` is logged in the ledger of the run its `--run` names when that run exists, otherwise in the active
  run's; a `--run` naming no existing run logs nothing.
- A `pnpm aegis` call carries `AEGIS_AGENT=<caller>` (`owner` for the main thread) and must be a command that caller
  may run; `aegis align`, `init`, `update`, `doctor` and `reconfigure` are the owner's.
- A `qa-*` agent dispatches only `qa-*` agents, never `qa-orchestrator`.
- Paths are compared physically: each existing component is realpathed before a `..` climbs, and only the part not
  created yet is normalized as text, so a symlink cannot carry a write past a rule. A subagent may not climb with
  `..` out of a directory that does not exist yet, nor link (`ln`, symbolic or hard) into `runs/` or the framework.
- Without a build, or on a guard error, the hook fails closed for `qa-*` agents, for other subagents whose call names
  a path inside this repo, and for main-thread calls whose path fields or unquoted command text name the runs
  directory; anything else is allowed with a warning (a `systemMessage`).

Bash targets are parsed best-effort (redirections, `tee`, `cp`, `mv`, `rm`, `sed -i`, `rsync`, heredocs, `cd`,
`bash -c`); writes inside interpreters are not seen. The hash chain and `aegis integrity verify` make such writes
detectable (spec §4.4).

**Env-safety — `envVerdict(agent, phase, env, policy)`** (H1, the SubagentStart context and `aegis task claim`):
- Names match by short name (`SPECIALISTS` in `@qa/contracts`); agent names are normalised
- If the env is read-only (`readOnly: true` or `mutating: false`) AND the specialist's `mutates` flag is set → refused
- If the specialist is in `forbiddenSpecialists`, or `allowedSpecialists` lacks both `*` and the specialist → refused
- A non-specialist is refused on a read-only env in a phase where its role changes the environment (`mutatesEnvIn`,
  e.g. the environment engineer in Env-data)
- On a refused claim the CLI records `env.specialist-blocked` and the claim fails with `env-blocked`; H1 denies every
  write of a refused agent

**Stop check — H2 (`scripts/hooks/require-work-report.mjs`, SubagentStop):**
- Only a call that carries `agent_id` and a `qa-*` `agent_type` is checked; the main thread and other subagents stop
  freely. Exit 2 keeps the subagent working, with the reason on stderr. Every other outcome exits 0, and a warning
  goes to stdout as a `systemMessage`. A missing build or an internal error lets the stop through, because the phase
  barrier still refuses unreported or unreviewed work.
- A worker is judged only on the tasks its own instance claimed, from the hook ledger (the `hooks/agents.jsonl` file of
  the active run). H1 logs a claim before the CLI runs, so H2 acts on a claim only when the task file confirms it: the
  task is in progress under that agent type, and this instance's ledger claim is the latest one at or before the
  task's `claimedAt`. A refused claim, or `task claim --help`, neither blocks nor releases.
- Every allowed stop appends a `stopped` ledger entry. Once the holder has `stopped` or `stop-unresolved`, the claim
  passes to the latest instance of the same type that tried to claim the task after `claimedAt` and has not ended.
  That instance is a resumed worker, which the CLI told to continue without claiming. A live parallel duplicate never
  inherits the claim.
- **Claim race (known limit).** The ledger is matched to the claim by time, not by identity. Suppose two instances
  of one type try to claim the same task at once, and the first one's claim command starts later. H2 can then pick
  the wrong instance as holder. That instance is held or released in the other's place. The phase barrier still
  checks the work itself. Binding a claim to its instance waits for the P0c caller-ticket design.
- A claimed task without a work report from this claim blocks the stop. A fresh report that was never released is
  released `done` for the worker. "Fresh" is the same rule `aegis task release` applies (`freshAttempt` in
  `packages/@qa/run-state/src/tasks.ts`). An attempt with a review or an escalation decision is not fresh, so a
  retried task needs a new report. Only a missing report blocks. When the release on the worker's behalf is
  refused for another reason, H2 re-reads the task. It skips a task that is no longer held, and otherwise lets the
  stop through with a warning.
- An SPV may stop once it has submitted a review since its `start` ledger entry, or when no released report of a
  paired worker awaits review.
- `qa-test-executor` holds its task until every specialist task of its phase is settled. While one is not, its stop
  without a work report is blocked with the loop instruction (`aegis task next --phase <id> --wait 540`, with what is
  running, offered and awaiting review), never with "submit your work report". With an open escalation, a blocked run or
  a stop request it may stop once nothing it dispatched is running, dispatched or under review: its task stays claimed.
- One instance is blocked at most 3 times. After that the stop is allowed with a warning, and the ledger records
  `stop-unresolved`.
- **`token.used` limitation (AUD-042b).** SubagentStop passes the session transcript (`transcript_path`), not a
  per-agent one. H2 counts only transcript lines whose `agentId` equals the stopping `agent_id`. It also reads the
  per-agent file Claude Code keeps beside the session transcript (`subagents/agent-<agent_id>.jsonl` in the session's
  folder), under the same per-line rule. That file layout is observed, not documented. When no line can be
  attributed, H2 records no `token.used`, and appends a `token-unattributed` ledger note instead. Token totals are
  therefore a lower bound: an agent missing from them has no attributable usage, not zero usage. A message id counts
  once, with the largest numbers seen across its repeated stream lines. A continued agent is charged only for entries
  after its last `tokens-recorded` ledger entry. That entry is written only when at least one event was recorded.
  When the bus refuses every event, a `token-unattributed` note carries the error, and the next stop retries.

### Checking the executive documents before a dispatch

`node scripts/check-executive-conditions.mjs --run=<RUN-id> [--dir=<folder>]` reads `technical-report.pdf`, `signoff.pdf` and `executive-deck.pdf` (default folder: the run's `reports/executive`) with `pdftotext`, reads `reports/closure/closure.json` and the defect records, and prints a pass/fail table for each of the three documents with the closure value and what was found, so the gaps are found before a dispatch and not one per attempt. Every expectation is computed from `closure.json`; no run figure is written in the script. The checks: (a) case figures, (b) out-of-scope cases with their reason, (c) every open application defect with its severity word and Awaits (the deck: the count and the Major/Minor split), (d) fixed, reframed and report withdrawn counts, (e) "N of M exit criteria are met" computed from the `met` flags, each unmet reason and each qualification, (f) the false passes: the closure's note that they are our own mistakes, its mechanism, every case id and the wrong-step text, (g) every item of `ownMistakesCorrected`, (h) the compliance totals (the sum of `complianceFindings[].coverageGaps`, the count of `highRatedGaps`) and the no-verdict sentence, (i) the open-question count and, in the technical report, every question id by audience, (j) no placeholder ("not available", "n/a", "undefined", "NaN", "null") where a figure belongs, (k) the wording tiers (tier 1 in all three, tier 2 in the sign-off and the deck, with line numbers), (l) identifiers intact, (m) the closure's reconciliation printed once. The deck is business language with no case ids, so the id-level checks (b), (f), (g), (i) and (m) ask of it only the counts and phrases it can carry; a check that does not apply to a document shows `n/a`. Exit 0 only when every check passes for every document, 1 when a check fails (the failing checks are listed), 2 for a missing input, 3 when `pdftotext` is missing (it says so and checks nothing). The checker is read-only: it writes nothing, so no role-table or hook rule is needed; `qa-executive-reporter` and its reviewer run it from Bash like any `node scripts/...` command, and so may the orchestrator and the owner. A passing checker is evidence, not a verdict: the reviewer still reads the documents.

## 13.4 Agent-memory dedup algorithm

When `proposeLesson(candidate)` is called:
1. Normalize the candidate's `rootCause` string (lowercase, strip punctuation, split into token set)
2. For each existing entry: compute Jaccard similarity = |A∩B| / |A∪B| on token sets
3. If max similarity ≥ 0.7: this is a near-duplicate → increment `hitCount` + update `lastSeen` on the existing entry; discard candidate
4. If no match: proceed to conflict check
5. Conflict check: if new `correctiveRule` is semantically opposite to an existing rule → emit `lesson.conflict-flagged`; do NOT append; escalate to curator
6. Assign the id (`L-{INITIALS}-{NNN}`, next free number of this agent's lessons file; see 7.2) and validate via Zod
7. Cap check: if active entries count ≥ 50 → evict lowest hitCount oldest entry to archive
8. Append; release lock

When `aegis review submit` pipes a `CorrectiveInstruction` and the lesson cannot be written (conflict, schema refusal, unreadable lessons file), the review is still recorded: the instruction stays in the review file, the CLI prints a `warning:` line on stderr and lists it under `warnings` in its result, and the chain gets `lesson.conflict-flagged` or `lesson.schema-rejected` (with `taskId`, `reviewPath`, `instructionIndex`).

## 13.9 Crash recovery (`/qa-resume`)

```
/qa-resume --run=RUN-20260523-001
```

1. Read the Taskmaster task tree for the run
2. Find all tasks with `status === "in-progress"` that have no recent event (stale > 5min)
3. Release orphan locks on those tasks (reset to `status === "pending"`)
4. Find the last `status === "done"` task (last completed step)
5. Resume from the next pending task in the dependency order
6. Emit `run.resumed` event

If a lock file is stale but the task is still running (e.g., the agent is just slow), `/qa-resume` will not interrupt it — it only releases locks with no heartbeat activity for > 5 minutes.

**Orphan run directory.** `aegis run create` appends `run.created` before it writes `run.json` and points `runs/.active` at the run. A crash in between leaves a `RUN-*` directory with no `run.json`: it is inert (no command treats it as a run, `runs/.active` still names the previous run, and the next `run create` takes a new id) and safe to delete.

## 13.10 Reissuing a phase of a completed run (`/qa-reissue`)

A completed full run is not final after Gate 1. `/qa-reissue --phase=<id> --reason="..." [--cases=...]` runs `aegis run reissue`, which only the owner can run. It accepts a completed full run and a phase after Gate 1's phase (Design through Curator); the reissued phase and every later one up to Executive reopen, but the curator runs once per run, so only a reissue of `curator` itself reopens it. Planning and every earlier phase, Gate 1 and the event history stay as they are.

1. The CLI verifies the event log, then records every work-report attempt on the tasks of the reissued phase and of every later phase as superseded in `run.json`, so only new work passes their barriers.
2. Those tasks go back to `pending` when they were `done` or `failed`; the reissued phase and every later phase go to `pending` (a completed phase after a reset gate is never reused), except the curator, which runs once per run and stays completed unless `curator` itself is the reissued phase, and the run to `running`.
3. Every gate after the reissued phase becomes `reset`: decided before, it needs a new owner decision. It is neither open nor approved, so the earlier phases run first, and when its phase completes the orchestrator opens it again. Its decision count is kept, so the new decision takes the next sequence.
4. One `run.reissued` (run id, phase, reason, reopened phases and gates, and the case list when given) is recorded, `run.json` keeps the same facts as its `reissue` record (replaced by the next reissue; the log keeps every one), and the run becomes the active run, because path-guard resolves the run folder through the active-run pointer.
5. The current decision file of each reset gate moves to `gates/gate-<N>-decision.<sequence>.json`, so the sign-off script and the orchestrator find no current decision until the owner decides again. A move that fails leaves the file, which the next decision archives anyway.
6. `/qa-reissue` dispatches the orchestrator, which re-runs the reopened phases, stops at each reset gate for `/qa-gate-decide`, and closes the run again with `aegis run complete`: the log then holds a second `run.completed`.

`--cases` scopes a reissued Execution: the executor dispatches only the listed cases, every other case keeps its recorded result, and each reopened specialist task outside the list gets a short carry-forward attempt. The case list applies only until a gate rejection or a completed run: a rejection decided without `--cases` lapses it (the rejection note then governs the scope), and once the reissued run has completed nothing is carried forward by scope. A rejection decided with `aegis gate decide --cases <ids>` (`/qa-gate-decide --cases=...`) instead sets the case scope itself, also in a run that was never reissued: the ids (comma-separated, trimmed, deduplicated, each a case design of the run, none descoped) are recorded in the gate decision file and in `gate.decided`, and the latest of such a rejection or a reissue with `--cases` is the list in force, until a rejection without `--cases` or a completed run. `--cases` is refused on an approval; at G1 (Design runs again in full after it, so the scope would only weaken the Design checks); at G3 (it reopens only phases after G2's, which come after Execution: the refusal points to `/qa-reissue --phase execution --cases <ids>`); when the run has no case designs yet; and unless the rejection reopens Execution or an earlier phase (a G2 rejection reopens Triage by default, so it needs `--reopen-phase execution` or earlier; the refusal names that fix). The data checks (the Blocked cause rule, the Design checks) read this scope the same way as a reissue's. **Carry-forward stamp.** A work report whose summary begins "Carry-forward attempt" (a summary that leads with the carry-forward words and names an attempt, such as "Carry-forward settlement", "No-op carry-forward", "Carry-forward re-verification", "Carry-forward under ...", "Carried forward from attempt ..." or "Carry-forward: " followed by what stands, such as a prior result that stands, is rewritten to begin with it, and the submit result lists the change under `adjusted`; a summary that only talks about carry-forward, such as "Carry-forward is not applicable", "Carry-forward: not applicable" or "Carry-forward: none this round", is left alone and not stamped) is stamped by `aegis work-report submit` with `carryForward: { eligible, reason }`; a stamp the worker wrote is dropped and the result says so. `eligible` is `false` when no case list is in force (none was set, or a rejection without `--cases` or a completed run lapsed it) or when the task's latest dispatch names listed cases, `null` when the list is in force but no dispatch of the task names any case (never `false` on missing data), and `true` otherwise. The stamp never refuses a report: the SPV reads it, a `true` allows the shortcut review (the named result files exist unchanged and nothing new was written), a `false` means the full checklist, not a rejection for being a carry-forward attempt, and a `null` or no stamp leaves the earlier prose rule. Reports stored before the stamp validate as they were. A reissue of a run that is not completed (a second one before the first finishes), of a smoke run, of a phase that is not completed in the run, of a phase at or before Gate 1, with `--cases` for a phase after Execution or naming a descoped case, with a malformed or unknown case id, or of a run whose log fails verification is refused. Every reopened phase overwrites its artefacts in place: copy the closure report and the PDFs first when they must be compared. To republish the corrected reports to the collector repo, run `/qa-push-reports --project=<name> --force` (`<name>` is the project's directory name under the QA folder). `--force` re-exports every run of that project (one export each), and the collector keeps one entry per run id, so the corrected run replaces its earlier copy. To republish only the reissued run, run the collector's export script for that single run from the Aegis repo root: `scripts/export-run.sh --project <name> --run <runId> --source <QA folder>/<name>/aegis/runs` (it commits and pushes, as `/qa-push-reports` does).

**Descoping a case (`/qa-descope`).** `/qa-descope --case=TC-... --reason="..."` runs `aegis run descope` (owner only, any run status; `--case` repeats for several cases, validated all or nothing): it appends the case and the owner's reason to `descoped` in `run.json` and records `run.descoped`; a second call for the same case changes nothing. The reports quote the reason, so the CLI refuses one that names the framework or an agent. `aegis metrics coverage` then leaves the case out of every count and out of the uncovered checks, reports it under `outOfScope` and `descoped` with its reason, and drops a requirement row whose cases are all descoped from the requirements coverage; the closure and executive reports state out-of-scope checks apart, with their reason.

**Correcting records after a gate decision.** When a gate decision demands a changed defect record or RTM link, `qa-defect-manager` (or the owner) uses the CLI; the closure reporter's role row cannot write `defects/**` or `rtm.json`, and nothing edits `events.jsonl` or a record's `history`.
- `aegis defect amend --defect <DEF-ID> (--set <field>=<value> ... | --json '{"<field>": <value>}') --reason <text>` changes only `retestVerdict.*`, `g2Triage.*`, `status.code`, `status.transitionedAt`, `requirementId` and `userStory` (the last two checked against the REQ and STORY id formats, so a wrong requirement link can be corrected; the objects `retestVerdict` and `g2Triage` may be set whole, to add a missing retest verdict). A value is JSON when it parses as JSON (`null`, numbers, objects), else text. The command refuses a field outside the list, an empty reason, new text that names the framework or an agent, a change that equals the record, and a result that adds a schema issue the record did not already have. It writes `defects/<DEF-ID>.json` atomically under `run.lock` and records one `defect.record-amended` (defect, agent, reason, and per field the path, old and new value and the SHA-256 of each); if the event cannot be recorded the old file is put back. An agent may run it only while the run is running; the owner also on a stopped, blocked or completed run. The `.md` twin of the record is not touched: the defect manager updates it.
- `aegis rtm unlink --defect <DEF-ID> --requirement <REQ-ID> --reason <text>` removes the defect id from the `defectIds` of that requirement's row of `rtm.json` and records `rtm.link-removed`; it keeps the `defectMap` entry of the pair (the event says `defectMapEntryKept: true`), because the entry carries the plan-time columns (acceptance criteria, wave, fix, notes) that a later sync cannot restore; `--drop-map-entry` (reason still required) also removes it (`defectMapEntriesRemoved`), after which `rtm sync-defects` re-creates it with default columns and lists the id as `recreatedWithDefaults`. A pair that exists only in the map has its entry removed. The rest of the file is untouched. It refuses a pair that is in neither the row nor the map.
- `aegis rtm sync-defects --reason <text>` (qa-defect-manager and the owner) makes `rtm.json#defectMap` match the defect records: one entry per record with `severity`, `title`, `requirementId` and `storyId` (the record's `userStory`) taken from the record; `retestCaseId`, `caseOrigin`, `acIds`, `wave`, `fixPr`, `verdictOracle`, `note` and any other key of an existing entry are kept, a new entry gets the record's `testCaseId`, empty lists, null wave and fix and a note; an entry whose defect has no record, or a second entry of one defect, is removed. A defect is added to the `defectIds` of the row its record's `requirementId` names (the record's own explicit link, so nothing is guessed) only when it is an open application defect (the `openApplicationDefects` rule): a FIXED, REFRAMED or REPORT WITHDRAWN defect gets no row link, because the owner may have unlinked it on purpose. A link in another row is never removed, because a defect may sit on several rows: `rtm unlink` removes it; `--prune-rows` (reason still required) also removes the row links of REFRAMED and REPORT WITHDRAWN defects and lists them as `rowLinksRemoved` in the event. An untraced record gets an entry with a null requirement. Nothing else in `rtm.json` changes. One `rtm.defect-map-synced` event carries the added, updated and removed defect ids, the row links added and whether `rtm.md` was updated. A run already in sync changes nothing and records nothing. `rtm unlink` also removes a pair that exists only in the `defectMap` (and refuses one present nowhere).
- `rtm.md` is written by hand by `qa-test-designer` (prose, execution waves, candidate map), so it cannot be rendered whole. Its defect-to-case table (the section headed `## Defect-to-case map`) is deterministic and is the one part the CLI owns: `aegis rtm render`, `rtm sync-defects` and `rtm unlink` rewrite that table and its count from the `defectMap`, and `rtm.rendered` records a standalone render. Everything else in `rtm.md` stays; after a correction nobody edits the table by hand.
- The orchestrator dispatches the corrections as a task of `qa-defect-manager` in the first phase after the decision, before the closure reporter's task; the start of the next metrics phase (Closure-final, then Executive) refreshes the rollups so they read the corrected records, and a correction made once the closure reporter has started needs `aegis metrics all` by hand.

**Case of record (`caseOfRecord`).** `aegis metrics coverage` counts one outcome per designed case: the worst of its ordinary result files (`TC-X-result.json`, `TC-X-<viewport>-result.json`). A case can have a further result file, `TC-X-result-<label>.json` (for example the messaging stub's angle next to the API angle's file); it is ignored by default. When the owner's gate decision names which result stands for a case, the executor puts that decision, word for word, in the brief of the specialist that wrote the file (the executor edits no result file and never picks a case of record itself), and the specialist adds to that file `"caseOfRecord": true`, a required `"caseOfRecordReason"` (the decision) and optionally `"supersedes": ["TC-X-result.json"]`; a file that is not the case of record may say `"observationOf": "<file>"`. The rollup then counts that file alone for the case, in place of the worst-first rule, and `coverage.json` gains `caseOfRecord` (`{ caseId, file, reason, supersedes? }`) and `observations` (every other result file of the case: `{ caseId, file, status, supersededBy, observationOf? }`), uncounted. Two files declaring the same case, or a declaration with no reason, make the command refuse (exit 2) naming the case and the files. A run with no declaration reads and writes exactly what it did before.

**Defect headline numbers (`totalOpened` versus `openApplicationDefects`).** `totalOpened` (of `defect.management-complete` and `defect-trend.json`) counts only the `defect.opened` events of the run: the defects it raised. It leaves out defects carried from an earlier run and retested, and it still counts one that was later reframed or withdrawn, so it is never the headline. The headline is `openApplicationDefects`, derived by `aegis metrics defects` (read-only; the owner, `qa-defect-manager` and `qa-closure-reporter`) from the defect records: a record with a `retestVerdict.verdict` is open exactly when the verdict is `NOT FIXED`, `PARTIALLY FIXED` or `CANNOT VERIFY`; a record with none is open when its status is neither closed nor flagged for the owner. `PARTIALLY FIXED` means something still has to be fixed, so it stays open until the remainder is fixed or the developers confirm the current fix resolves everything. `FIXED`, `REFRAMED` and `REPORT WITHDRAWN` are not open application defects. The command counts each verdict as `fixed`, `partiallyFixed`, `reframed`, `reportWithdrawn`, `cannotVerify` and `notFixed`; `partiallyFixed`, `cannotVerify` and `notFixed` are subsets of the headline: `openApplicationDefects` = `notFixed` + `partiallyFixed` + `cannotVerify` + the open records with no verdict. It also prints `openItems`, the open records grouped by verdict (`NOT FIXED`, `PARTIALLY FIXED`, `CANNOT VERIFY`, `NO VERDICT`), each with id, title, severity, status and what is awaited (developer fix; developer fix or confirmation; a retest that can reach a verdict; triage and a PM decision), so the closure lists each one without counting by hand. The defect manager copies the figures into `defect.management-complete`, `aegis metrics all` into `defect-trend.json`, the closure reporter states `defectMetrics.confirmedOpen` as `openApplicationDefects`, and the sign-off and technical report (`resolveDefectFigures`) apply the same verdict rule to the records when `confirmedOpen` is absent. `severityBreakdown` counts the open application defects by severity, so `aegis event append` refuses a `defect.management-complete` whose breakdown does not sum to its `openApplicationDefects` (the message names both numbers). A corrected event may be appended later: readers use the last `defect.management-complete` of the run (`latestDefectManagementComplete` in `@qa/metrics`), and events are never edited or deleted. All seven fields are optional: an event or file written before them reads as before. After a record correction (`aegis defect amend`) the counts are read again.

**Metric files (`aegis metrics all`).** No agent writes a metric file: the retired metrics collector was a model dispatch that only ran this command. `aegis phase start` for Closure-draft, for Closure-final and for Executive (full cycle) runs it in its own process, under the run lock, before it marks the phase started (the cycle event needs Executive still pending); no process is spawned, and the start prints `metrics` (what was written) in its result. A refusal (a malformed case-of-record declaration) never refuses the start: the files stay as they were and the result carries `warnings` naming the cause. The orchestrator runs `aegis metrics all` by hand only to refresh the files after a refused refresh or after a record correction made once the closure reporter has started. The Closure-final barrier warns (never refuses) when a metric file is missing or when the check counts in `coverage.json` differ from a recompute from the case files. The command computes `cycle-time.json`, `coverage.json`, `defect-trend.json`, `effectiveness.json`, `agent-reliability.json` and `flaky.json` from `events.jsonl` and the case, result, defect and plan records (definitions in `packages/@qa/metrics/src/rollups.ts` and `coverage.ts`), computes all six before writing any, replaces them atomically in `reports/metrics/` (a path only the CLI writes), and prints `written`, `missingInputs`, `notes`, `phaseRollups` and `cycleComplete`. After the files it appends the cycle events: one `metrics.phase-rollup` (`phase`, `durationMs` of its latest completed pass) for each completed phase that has none in the log, and, when the run is a full cycle whose Closure-final has completed and whose Executive has not started (the call before Executive, in a reissued run too), one `metrics.cycle-complete` with `totalDurationMs` (the `totalWallClockMs` of `cycle-time.json`, gates included) and `totalTokensUsed` (the sum of `input`, `output` and `cached` of every `token.used` event; 0 without one). The orchestrator and the owner may run it; `aegis metrics coverage` and `aegis metrics rollups` stay as its two halves, run by the owner for diagnosis (`qa-defect-manager` may run `rollups --check`, which prints and writes nothing). An empty source gives its empty shape: `flaky.json` is `[]` without a retried test, `cycle-time.json` `{ "phases": [], "totalWallClockMs": 0, "bottleneckPhase": null, "noData": true }`, and every other object file zero counts and empty lists with `noData: true` (`defect-trend.json` without a `defect.opened` event is a real zero count and has no `noData`). Nothing is 0 for unknown: a figure that cannot be computed is null, a missing input is listed, and a missing log marks the file `noData`. Where the old prose was ambiguous the stricter reading was taken:
- cycle-time: one entry per pass of a phase (a phase run again after a rejection or reissue has an entry per pass); `agentName` is the phase's agent (the orchestrator for Intake and Compliance); a pass still running has no `completedAt` and no `durationMs`.
- `reopenRate`, `escapeRate` and `dre` are percentages (0-100, one decimal), the scale of the closure metrics; `defectDensity` is opened defects per 100 designed (in-scope) cases, two decimals, because no story points are recorded.
- An escaped defect is one whose record says `foundIn: Prod` or whose `phaseIntroduced` names a post-release phase (the phase enum has none); `dre` = (opened - escaped) / opened.
- `mttdMs` uses the first earlier `test.failed` event of the defect's test case; `mttrMs` the first later `defect.closed`; an opened defect with no record counts under `Unknown` in `byPhaseIntroduced`.
- `testsExecuted` counts designed cases with a result that ran to a verdict (not blocked, skipped or undeterminable); `byTestType` counts each defect-finding case under each of its `testType` values.
- `agent-reliability`: `reviewPassRate` counts `review.passed` and `review.passed-with-notes` over those plus `review.requested-changes`, null without a review; `lessonAppendCount` counts `lesson.appended` events, and `aegis review submit` records none, so 0 means none recorded.
- `flaky.json` is the plain array unless a case is only suspected: a case that failed then passed is flaky only if every earlier failing attempt in its result file (`priorResults[]`) records `origin` or `failureOrigin` test-side, environment or flaky; otherwise the file becomes `{ flaky, suspectedFlaky }` with a reason. A TC has one row; its per-viewport files win over the plain file.

**Metric file definitions** (what `aegis metrics all` writes; the code in `packages/@qa/metrics/src` implements exactly these, and the tests pin each shape).

Every call of `aegis metrics all` writes every metric file below, whether or not it has data for it: `cycle-time.json`, `coverage.json`, `defect-trend.json`, `effectiveness.json`, `agent-reliability.json` and `flaky.json`. The closure reporter requires the six `.json` files and never waits for one, so a file left out would be a hole in the closure report. A rollup without source data is written in its empty shape: `flaky.json` is `[]` when no test was retried, and an object file holds zero counts and empty lists plus `"noData": true`, so its reader states the figure as not available instead of 0. One exception: `defect-trend.json` with no `defect.opened` event is data, not an absence — zero defects opened is a real count (see "Defect metrics" below).

**Token total (from `token.used` events; no file).**
The SubagentStop hook (require-work-report) records `token.used` once per subagent run, one event per model, from the transcript entries marked with that subagent's agent id: `input` is the input plus cache-creation tokens, `output` the output tokens, `cached` the cache-read tokens. When the transcript attributes nothing to the subagent, the hook records no event, so a missing agent means no attributable usage, not zero usage.
No token file is written and no cost is computed. The only token figure is `totalTokensUsed` of `metrics.cycle-complete`: the sum of `input`, `output` and `cached` over every `token.used` event in the log (0 when there is none).

**Cycle time (from `run.phase.started`, `run.phase.completed` events).**
Output: `runs/{runId}/reports/metrics/cycle-time.json`, exactly `{ phases: [{ phase, startedAt, completedAt, durationMs, agentName }], totalWallClockMs, bottleneckPhase }`.
- `phases`: one entry per phase, `startedAt` and `completedAt` ISO timestamps (`completedAt` absent while the phase runs), `durationMs` = `completedAt` − `startedAt`, `agentName` the phase agent.
- `totalWallClockMs` runs from the run's start (the first `run.phase.started`) to the last `completedAt`, including the time spent waiting at gates, so it is not the sum of the phase durations. The technical report reads it first.
- `bottleneckPhase`: the phase with the longest `durationMs`.
With no completed phase the file is `{ "phases": [], "totalWallClockMs": 0, "bottleneckPhase": null, "noData": true }`.

**Coverage.**
`aegis metrics coverage` (also run by `aegis metrics all`) computes it: the command reads `rtm.json`, the case and result files, `reports/unit-coverage.json` and the cases the owner descoped (`run.json`), and writes `reports/metrics/coverage.json` itself. No agent computes these figures by hand or writes that file; the rules below say what the command does.
- **Requirements coverage**: the rows of `rtm.json` (a top-level array of rows, or an object whose `rows` is that array) whose `testStatus` is `Covered` / all rows, as a percentage with one decimal. A `Partial` row is not covered; the command counts those apart as `partialRequirements`.
- **Test execution coverage**: TCs designed (`cases/{TC-ID}.json`) that were executed / TCs designed. The outcome of a TC is its worst outcome, in this order, worst first: `fail`, `blocked`, `partial`, `skipped`, undeterminable (a result with no determinable status), `pass`, `no-op`. A TC is executed unless that worst outcome is `blocked`, `skipped` or undeterminable, so a failed, partial or `no-op` outcome is executed, and a TC with no result file is not executed. A TC is passed only when every one of its outcomes is a pass or a `no-op` (`no-op` counts as a pass, as in the `passed` count). A result file holding a `results[]` array counts as its worst sub-result, by the same order (`fail` with `blocked` is `fail`, so executed). Result files come in two layouts: `cases/{TC-ID}-result.json` and the responsive specialist's `cases/{TC-ID}-{viewport}-result.json`. A TC id matches `^TC-[A-Z]{2,8}-\d{3,}$`, a viewport is one of `desktop`, `tablet` or `mobile`, and a file name is parsed as the TC id, an optional `-{viewport}` and `-result.json`. A TC counts once, however many of its files exist. When both layouts exist for a TC, the per-viewport files win and the plain file is ignored. For a TC with viewport files, the outcomes are those of its viewport files plus one undeterminable outcome for every viewport in its `viewportScope` (from `cases/{TC-ID}.json`; all three when absent) that has no result file, so a missing viewport is never dropped: it makes the TC not passed, and not executed unless another viewport's outcome is `fail` or `partial`.
- **Code coverage**: from the unit specialist's `runs/{runId}/reports/unit-coverage.json` (`lines`, else `statements`), if it exists; absent, the code-coverage figure is not available (no 0).
- **Counts**: one outcome per designed TC, by the worst-first order above, tallied as `designed` (TCs with a design file), `attempted` (designed TCs with a result file; a result whose TC has no design file is ignored), `passed` (worst outcome `pass` or `no-op`), `failed`, `partial`, `blocked`, `skipped`, `unknown` (undeterminable) and `notAttempted` (designed minus attempted). Note that executed (`testExecutionCoverage`) means the check ran to a verdict: passed, failed or partial; attempted also includes blocked, skipped and undeterminable results. The six outcome counts add up to `attempted`, and `attempted` plus `notAttempted` is `designed`. Counts are computed by the command from the case files, never by hand: they are the one source for every count the closure and executive reports state, and where `execution-summary.json` or `closure.json` differ, `coverage.json` wins.
- **Uncovered checks**: every check that gave no verdict: the blocked, skipped and undeterminable ones and the designed ones with no result file, each with one cause, computed by the command and nowhere else. A check with no result file is `not-attempted`, and only such a check is. For any other uncovered check the cause is the first match of the command's keyword table on the text of its result files (their notes, note, blocker, blockedReason and reason; for a `results[]` file only the entries that gave no verdict, never a passing one), else on the origin text of that check's row in the closure's table of uncovered test cases, else `testing-side` when a scoped viewport has no result, else `other`. No document supplies a cause: a `cause` written on a closure row is ignored. The command writes `uncovered` as `{ byCause: { environment, testingSide, requirementGap, notAttempted, other }, rows: [{ id, cause, via }] }`; the `byCause` counts add up to `blocked` plus `skipped` plus `unknown` plus `notAttempted` of `counts`. No agent classifies a row by hand.
- **Out of scope**: a case the owner descoped (recorded in `run.json` with its reason) is out of scope: it is in none of the counts (not `designed`, not `attempted`, no outcome, not `notAttempted`) and never an uncovered row, even when it has a result file, and the test execution coverage is computed over the in-scope cases. `counts` then carries `outOfScope`, the number of descoped cases that have a design file, and `coverage.json` carries `descoped`: one `{ caseId, reason }` per such case, sorted by id. Both are absent when no designed case is descoped. A requirement row whose linked cases are all descoped leaves the requirements denominator; a row with some descoped cases counts by its in-scope cases only: `Covered` when every one of them passed, `Partial` when at least one did, otherwise not covered. A row with no descoped case counts by its recorded `testStatus`, as above.
- **Case of record**: a result file of a case may declare itself the case of record with `"caseOfRecord": true` and a required `caseOfRecordReason` (optionally `"supersedes": [<result file names>]`); it is written only when the owner's gate decision names it. Further result files of a case are named `{TC-ID}-result-<label>.json` and count for nothing otherwise. For a case with a declaration, the case's outcome is that file's outcome alone, in place of the worst-first order, and `coverage.json` lists the case under `caseOfRecord` (`{ caseId, file, reason, supersedes? }`) and every other result file of it under `observations` (`{ caseId, file, status, supersededBy, observationOf? }`), uncounted. Two files declaring one case, or a declaration without a reason, make the command refuse with the case and file names: report that to the orchestrator, never edit a result file. Both keys are absent when no case declares one.
Rollup: percentage per type.
Output: `runs/{runId}/reports/metrics/coverage.json`, exactly `{ requirementsCoverage, testExecutionCoverage, codeCoverage, partialRequirements, counts, uncovered, descoped?, caseOfRecord?, observations?, noData? }`, where `counts` is `{ designed, attempted, passed, failed, partial, blocked, skipped, unknown, notAttempted, outOfScope? }` (whole numbers, all zero when `noData` is true except `outOfScope`; `uncovered` is then empty with all causes zero; `outOfScope` and `descoped` appear only when a designed case is descoped, also when `noData` is true, see Out of scope): percentages from 0 to 100 as plain numbers; `codeCoverage` is a number or null (null when `unit-coverage.json` is absent); `noData: true` only when `rtm.json` or the case files are absent or empty, or every designed case is descoped. The closure reporter copies `requirementsCoverage` into `closure.json#metrics.requirementsCoverage`.

**Defect metrics (from `defect.opened`, `defect.closed`, `defect.reopened` events).**
- Total opened, closed, reopened
- By severity: Sev1-Sev5 breakdown
- By phase-introduced: where defects were injected
- Defect density (defects per story point if available, else per 100 TCs)
Output: `runs/{runId}/reports/metrics/defect-trend.json`, exactly `{ totalOpened, totalClosed, totalReopened, bySeverity, byPhaseIntroduced, defectDensity, reopenRate, escapeRate, mttdMs, mttrMs, openApplicationDefects?, fixed?, partiallyFixed?, reframed?, reportWithdrawn?, cannotVerify?, notFixed?, noData? }`. `bySeverity` has the keys `Sev1` to `Sev5`. `reopenRate` = reopened / closed; `escapeRate` = defects whose `phaseIntroduced` is after release / total defects; `mttdMs` = mean time from the first failing result of a defect's test case to its `defect.opened`; `mttrMs` = mean time from `defect.opened` to `defect.closed`. Each rate or mean is a number, or null when it cannot be computed (no closed defects, no timestamps) — never 0 for "unknown". `totalOpened` counts only the `defect.opened` events of this run, the defects it raised; it is not the number of open application defects (defects carried from an earlier run and retested are not opened here, and a defect opened here can be reframed or withdrawn). The headline defect figure is `openApplicationDefects`: `aegis metrics all` writes it with `fixed`, `partiallyFixed`, `reframed`, `reportWithdrawn`, `cannotVerify` and `notFixed` (counted from the records' `retestVerdict.verdict`; `openApplicationDefects` already includes `notFixed`, `partiallyFixed` and `cannotVerify`) after the defect records are final, and leaves the seven fields out when the run has no defect records. `aegis metrics defects` prints the same figures read-only, with the open items by verdict. Wherever a defect figure comes from a `defect.management-complete` event, use the LAST one of the run (a corrected event may follow a first; events are never edited). A log with no `defect.opened` event gives zero counts (0 opened, closed and reopened, every severity 0, density 0) with the rates and means null, written without `noData`. Write `"noData": true` only when `events.jsonl` is absent or unreadable. The closure reporter reports these as escapeRate, reopenRate, MTTD and MTTR.

**Test effectiveness.**
- Tests that found defects / total tests executed
- Defect detection by test type (E2E / API / unit / security / etc.)
Output: `runs/{runId}/reports/metrics/effectiveness.json`, exactly `{ dre, testsThatFoundDefects, testsExecuted, byTestType, noData? }`. `dre` (defect removal efficiency) = defects found before release / (found before release + escaped) × 100, a number from 0 to 100, or null when no defect exists to compute it from; `byTestType` maps each test type to its count of defect-finding tests. The closure reporter reports `dre` as DRE.

**Agent reliability (from `review.passed`, `review.requested-changes`, `task.claimed/released`).**
Per agent: `{ reviewPassRate, requestedChangesCount, meanTaskDurationMs, lessonAppendCount }`
Output: `runs/{runId}/reports/metrics/agent-reliability.json`.

**Flaky tests (from retry and attempt data; computed by `aegis metrics all`).**
Rule: a case that failed and then passed counts as flaky only if every earlier failing attempt in its result file records a non-application cause in `origin` or `failureOrigin` (`test-side`, `environment` or `flaky`); otherwise it is reported as `suspectedFlaky` (the file is then `{ flaky: [...], suspectedFlaky: [{ testRef, flakeRate, retryCount, reason }] }`; without a suspect it is the plain array).
- Per test: `{ testRef, flakeRate, retryCount }`, from the retry and attempt data in the result files, `runs/{runId}/cases/{TC-ID}-result.json` and the per-viewport `runs/{runId}/cases/{TC-ID}-{viewport}-result.json` of the responsive specialist (the glob `cases/*-result.json` matches both, parsed as in "Test execution coverage": a TC yields ONE flaky row, with `retryCount` the maximum across its viewport results and `flakeRate` computed from the same files, and the per-viewport files win over a plain file of the same TC) (a test that failed and then passed on a retry counts as a flake)
Output: `runs/{runId}/reports/metrics/flaky.json`.
